# 完整资料、来源与手动维护

## 1. 收集单位：一条可说明白的申请路线

同一个目的地，不同申请人范围、用途或办理渠道可能有不同费用、材料与时长。分别建立稳定 `routeCode`，例如 `JP-TOURISM-CN-RES-CN-STANDARD`。它只是命名示例，不是政策事实。不要把不同渠道最便宜的费用和最快时长拼成一条不存在的路线。

`data/templates/policy-template.json` 是完整空值模板，`shared/contracts.ts` 是机器可检查的字段约定，`database/schema.sql` 是唯一可执行建表版本。

| 资料组 | 必须调查并保留的内容 | 存储规则 |
|---|---|---|
| 国家／地区 | 两位代码、中英文名、区域、别名、目录来源、定位点 | 字典与地理目录不作为签证依据 |
| 路线 | 官方名称、用途、申请人范围、申请渠道、入境次数 | 事实未知可 null；发布需明确名称和适用范围 |
| 有效期 | 数值、日/月/年、起算或裁量说明、来源 | 数值和单位同时已知或同时 null |
| 停留期 | 时长、单位、每次/滚动期/官员裁量、限制说明 | 不把有效期当停留期，不把月直接乘 30 |
| 材料 | 逐项名称、详细要求、份数、是否必须、条件、来源 | 不只写“护照、照片等”；条件材料单列 |
| 费用 | 每项名称、金额范围、币种、计费单位、适用条件、包含与不包含内容 | decimal 字符串；0 才是免费，null 是未知 |
| 办理时间 | 范围、工作日/自然日、起算点、适用条件、说明 | 不能把预约等待与受理后处理混为同一时长 |
| 个人条件 | 护照签发地、居住地、年龄、身份、护照余期、已有签证限制 | 仅将能准确表达并有来源的条款写成可执行规则 |
| 核验 | 来源清单、逐字段引用、最近复核、建议下次复核 | 未复核不可伪填今天为已核验 |

技术标识、版本、状态和数组结构不是“收集不到的政策事实”，因此仍为必填。未知金额填 null，未知清单用空数组加 `UNKNOWN`；不能用空数组暗示无需材料。`PARTIAL` 表示还未收齐。确实无需材料时使用 `NOT_REQUIRED` 并在适用说明及其来源中记录依据。

`sources` 以 JSON 随路线保存，材料/费用/规则的 `sourceIds` 引用其中的 ID；这样一条路线可原样导出、检查、恢复，无需新增来源管理后台。若未来来源复用量很大，再由 A/B/C 协商迁移成独立来源表。

## 2. 每个事实能点开查证

一条来源至少包含：`id`、`title`、`url`、`publisher`、`kind`、`accessedAt`、`locator`、`status`。

- URL 必须是公开可访问的 http/https 页面；优先主管机关、使领馆，再授权受理中心、可靠成熟平台。
- `locator` 写“页面哪个章节/表格/页码/人群条件”，不能只给一个网站首页。
- `accessedAt` 为实际查阅时间，使用 ISO UTC 时间。链接可打开不等于内容适用于本路线。
- `VERIFIED`：B 已核对与该事实相关的来源和适用范围；`SINGLE_SOURCE`：仅有单一依据，明确保留该限制；`CONFLICT`：依据冲突；`UNAVAILABLE`：现不可访问；`DEMO`：虚构演示。
- B 对每批资料记录主来源、独立交叉来源、差异和处理结论。优先至少一个官方来源；权威页面没有写的内容不从平台猜补为“官方要求”。
- 两个网页复制同一段资料不能假装两个独立证据。成熟平台只能辅助，冲突时不自动取较新或较低费用。
- 真实公开的非空事实需要可用的字段级来源；冲突事实先设 null 或把整条路线 `isVisible=false`，在复核记录中保存待解决事项。
- 源码校验只检查格式、引用和状态，**不会访问网站替你验证真假或可达性**。管理员实际打开页面、核对内容后才能改状态。
- 链接需登录/有验证码/当前不可用时如实标记，寻找同一机构的替代公开说明；不要承诺永久可访问，不抓取私人内容。

## 3. 推荐规则的能力和边界

`IN` 用于枚举，`GTE/LTE/BETWEEN` 用于年龄或月数，`ANY_OF` 用于持有签证代码。多条规则按同时满足处理。签证代码表由 B/C 约定，UI 目前接受代码输入；仅填 `US` 并不能表达签证是否有效、多次、已使用等复杂要求，无法准确表达时不得把它写成完整资格规则。

复杂的“任一条件满足”“不同申请人交不同材料”“有某签证可豁免”保留原文和条件说明，`rulesStatus=PARTIAL`。优先拆成范围清晰的路线；确实需要复合规则再由 B/C 扩展，不能压扁为误导的判断。`COMPLETE` 指本项目明确声明范围内可判定条件已收齐，不代表穷尽法律上全部审查条件。

检查结果分为通过、未知、不符。资料过期、演示、缺规则、缺用户条件或币种不一致均不能直接当“符合”。预算只比较同币种、同路线标记为 `comparable` 的官方申请费，不包含旅行预算或全部附加费。每条路线至多一个可比较费用项、一个可比较时长项。

## 4. 管理员手动更新：先看计划，再写库

1. A 从模板复制并编辑完整路线批次。批次顶层是 `{schemaVersion:"1.0", datasetVersion:"唯一批次名", policies:[...]}`。
2. B 打开来源逐项复核，在对应数据 PR 留记录，决定发布、保留空值或暂不公开。
3. 本地 `.env` 配置管理员；先运行校验。管理员环境和资料库只在本机，不进入 Git。

```powershell
npm run data:validate -- data/batches/example.json
npm run db:import -- data/batches/example.json
```

第二条命令只生成计划，输出 `local/plans/<计划文件>.json`，不写政策。B 打开计划，看新增/替换的 `routeCode`、版本、数据内容，确认选的是自己的正确数据库。

```powershell
npm run db:import -- --apply local/plans/<计划文件>.json --confirm=<datasetVersion>
npm run db:export -- local/backups/after-update.json
```

尖括号是占位符，请替换成实际输出，不能原样执行。应用时重新核验内容和库版本，先落盘备份，然后事务更新；期间出错回滚。已有库在计划生成后变化，计划会拒绝，重新生成并人工检查。

**更新单位是完整路线**：同 `routeCode` 覆盖路线并替换其材料/费用/时间/规则。不是只传某个金额的部分补丁。数组缺失会被拒绝；误传空数组可能有清空含义，必须人工审阅。批次未列出的路线保持原样。下架使用完整路线 `isVisible=false`，不要物理删除历史事实。

默认禁止演示数据入库。如需测试，只对专用测试库暂时设置 `ALLOW_DEMO_IMPORT=true`，测试后关闭；真实资料库不允许这么做。

## 5. 回退与维护安排

- 应用前备份在被 Git 忽略的 `local/backups/`。保存一份到本机以外的受控备份位置；脚本不提供灾备平台。
- 回退时先比较备份与当前库，以备份为输入生成新计划，确认后应用；不能复用旧计划的摘要。
- 如果误新增了备份中不存在的路线，备份导入不会自动删除它，另建完整路线批次设置 `isVisible=false`。
- `refreshDueAt` 只是人工复核提示和推荐新鲜度判定，不启动定时任务。B 每次准备发布时检查到期条目，主动发现官方变更时立即复核；具体周期由资料风险决定。
- 更新 PR 记录“谁、何时、改了哪些路线、依据是什么、计划/备份在谁的机器”。公开仓库不能上传管理员口令、真实个人资料或带密钥日志。
- 资料更改会在下次 API 读取时生效；浏览器当前快照需点击刷新。界面显示的版本用于定位同一批资料，不承诺实时推送。
- 数据表变更另写带日期的迁移 SQL，经 A/C/D 检查后执行。`db:init` 只负责初始化，不会自动把旧表改成新结构。
