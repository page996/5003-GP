## 每份协议都遵循的约定

1. 角色实际姓名/账号、截止时间、交付版本/PR 和双方确认，由成员开工时填写。未填写不虚称已达成。
2. 所有影响字段、接口、文件归属、先后顺序或验收标准的沟通，都写入同一份双边协议的追加记录。可以链接 Issue/PR；不要求每聊一句就新建一个长文件。
3. 交付物至少包含：文件/版本、运行或校验命令、成功样例、失败/未知样例、剩余问题。不能只交截图、口头承诺或需要收件人重新拼装的代码片段。
4. 接收方依协议验收；不通过给出复现步骤、预期/实际、数据版本。修复归原作者，接口含义争议请双方和 D 确认，不擅改第三人的模块。
5. 不在协议/PR/聊天中传实际数据库密码、安全密钥或真实个人申请资料。运行环境按 `.env.example` 本地填值。
6. 任何人工或 agent 接手都先读取本协议、角色职责、`docs/API.md`、`shared/contracts.ts`，只修改约定范围。禁止改口径、删字段、把 demo 改名为真数据或为了通过测试降低断言。
7. 协议变更写新版本、兼容影响及迁移步骤；双方确认后同批更新调用者和测试。没有确认，继续旧约定或明确阻塞，不静默修改。
8. 初版目标是同一 base 的小增量；没有发生跨模块变化的 PR 可以引用已有已确认协议，不重复签长文。

## Agent 交接最短模板

```text
你接手角色：
对应协议及版本：
起点提交号：
本次目标：
允许修改的文件：
禁止改变的字段/业务：
输入文件与样例：
期望输出：
验证命令及手工步骤：
已知限制/需要对方先交付的内容：
```

每份配对文件末尾有确认和追加记录表。双边协议是为了减少误解，不是让 D 替所有人写会议纪要。
