# D｜前后端接线、测试统筹与版本验收职责书

## 你要做什么

让大家的改动在同一页面、同一 API、同一资料版本下工作，并把不合格提交退回原作者。你不是负责替全组补代码的人。

1. 接手 `client/App.tsx`、`client/api.ts`、构建接线与共用测试。国家选择只有一个共享状态，地图/列表/资料不能各选各的。
2. 维护加载、错误、空结果、重试、刷新和模式提示；真数据与 demo 标识不能混淆。
3. 先完成一条真实数据链路验收，再扩大国家批次。不要等 A/B 收完全部数据才开始。
4. 审每个 PR 的文件边界、接口版本、测试、来源与安全，核对对应双边协议；合格才合并。
5. 组织最终桌面 Web 验收和版本说明。列出已完成、未完成、已知问题，不用截图代替测试。

## 文件边界

主责总体页面状态、API 调用封装、构建接线、`tests/` 中跨模块用例、CI 与协作文档。功能作者应补自己模块的用例；你审核并运行，不包办所有测试。共用 CSS 由你协调 E/F 的具体区段，避免各自重写全站样式。

## 交付物

- 每次合并的 PR、版本/提交号、验收人及结果。
- 搜索→地图选择→完整资料→条件推荐的验收记录；未知、失败、过期、无数据的反例记录。
- MySQL 更新前后及回退演练结果；地图真实 Key 验收或明确未完成说明。
- 最新启动说明、已知问题、覆盖账本及对负责人可读的版本说明。

## 验收和退回

按 `docs/CONTRIBUTING.md` 执行自动与桌面人工检查。页面错误交 E 或 F，接口错误交 C，事实错误交 B，采集缺口交 A。注明复现步骤、预期、实际结果与路线号，避免只说“这里不对”。

直接相关的双边协议是 A-D、B-D、C-D、D-E、D-F。D 只汇总，不代替双方确认业务含义。主干保护、合并权限由仓库所有者实际在 GitHub 设置；文档/模板不等于权限已生效。
